# AetherShell

Платформа управления компьютерными клубами: один сервер обслуживает все клубы, владелец клуба входит в кабинет и получает установщик своего шелла, а на ПК клуба работает десктопная оболочка.

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│         AetherShell.Server (.NET 10, PostgreSQL, TLS)         │
│                     один хост, один origin                    │
│                                                              │
│  /            лендинг с формой заявки (AetherMain)            │
│  /cabinet     кабинет: список клубов, создание, установщик    │
│  /panel       админ-панель клуба (admin-panel)                │
│  /api/...     REST API, скоуп клуба по X-Club-Id / X-Club-Key │
│  /clubhub     SignalR: группы {clubId}:Admins, {clubId}:{pc}  │
│                                                              │
│  Одна база: ClubId во всех клубных таблицах + query-фильтры    │
└───────────────┬──────────────────────────────┬───────────────┘
                │                              │
      CLUB_KEY + HardwareId              уведомления
                │                              │
                ▼                              ▼
   ┌────────────────────────┐        ┌────────────────────┐
   │ ClubApp на ПК клуба     │        │ telegram-bot        │
   │ + SpikInstaller         │        │ (только заявки)     │
   └────────────────────────┘        └────────────────────┘
```

Два уровня входа, потому что это две разные аудитории:

- **`Account`** — платформенный аккаунт: `PlatformAdmin` (владелец шелла, видит все клубы) или `Owner` (владелец клуба или сети). Вход в `/cabinet`.
- **`User`** — персонал и посетители конкретного клуба. Вход в `/panel` и в шелл на ПК.

Владельцу не нужна строка в `User`: внутри своего клуба он получает права `Super`, поэтому админ-панель открывается тем же токеном.

## Компоненты

| Компонент | Технологии | Описание |
|---|---|---|
| `SpikServer` | .NET 10, PostgreSQL, SignalR | Единый мультитенантный сервер: API, хаб, статика |
| `admin-panel` | React 19, Vite, TypeScript | Панель управления клубом, отдаётся с `/panel` |
| `AetherMain` | HTML/CSS/JS | Лендинг и кабинет, отдаются с `/` и `/cabinet` |
| `ClubApp` | WPF (.NET Framework 4.7.2) | Оболочка на ПК клуба |
| `SpikInstaller` | WinForms (.NET 8) | Установщик оболочки, настраивается из `server.config` |
| `SpikWatchdog` | .NET 8 Worker | Служба, следящая за процессом оболочки |
| `telegram-bot` | Python 3.12, aiogram 3 | Уведомления о заявках с лендинга |

## Быстрый старт (Docker)

```bash
cp .env.example .env   # заполните DB_PASSWORD, SPIK_JWT_SECRET, AETHER_ADMIN_*, PUBLIC_URL
# Положите SpikInstaller.exe в deploy/installer/ — иначе кнопка установщика в кабинете не сработает
docker compose up -d --build
```

Сервер поднимется на `http://localhost:5232`: лендинг на `/`, кабинет на `/cabinet`.
Первый вход — под `AETHER_ADMIN_EMAIL` / `AETHER_ADMIN_PASSWORD`.

Папка `deploy/installer/` монтируется в контейнер: достаточно скопировать туда `SpikInstaller.exe`.

Telegram-бот заявок стартует вместе с сервером (локально — через `TelegramBotHostedService`, в Docker — сервис `telegram-bot` в `docker compose up`). Задайте `TG_BOT_TOKEN`, `TG_CHAT_ID` и `TG_BOT_SECRET` в `.env` / `telegram-bot/.env` или в `server-settings.json` (`TelegramBotToken`, `TelegramChatId`, `TelegramBotSecret`). Нужен Python 3 и зависимости из `telegram-bot/requirements.txt`. Чтобы отключить: `TelegramBotEnabled: false`.

### Обновление с версии до баз-на-клуб

У каждого клуба теперь своя база `aether_club_{id}`, поэтому старая единая база не
обновляется миграциями. Сервер распознаёт её на старте и просит пересоздать:

```bash
docker compose down -v && docker compose up -d --build
```

Данные не переносятся: клубы и компьютеры придётся подключить заново. Вне Docker
базу можно снести на месте, запустив сервер один раз с `SPIK_RESET_LEGACY_DB=true`
(в Visual Studio для этого есть профиль «Development (сброс старой базы)»).

### Обновление до общего клиента на сеть

Посетители переехали из баз клубов в платформенную таблицу `Clients`. Миграция
`StaffOnlyClubUsers` удаляет их старые записи из `Users` каждого клуба: балансы там
были свои у каждого филиала, и сложить их в один автоматически нельзя. После
обновления посетители регистрируются заново, персонал зала остаётся на месте.

### Без Docker

```bash
# 1. Панель: её dist копируется в wwwroot при сборке сервера
cd admin-panel && npm ci && npm run build && cd ..

# 2. Сервер
$env:SPIK_DB_CONNECTION="Host=localhost;Port=5432;Database=AetherShell;Username=postgres;Password=..."
$env:SPIK_JWT_SECRET="<случайная строка>"
$env:AETHER_ADMIN_EMAIL="admin@example.com"
$env:AETHER_ADMIN_PASSWORD="<пароль>"
cd SpikServer/SpikServer && dotnet run
```

Миграции применяются автоматически при старте (`Database.Migrate()`).

## Подключение клуба

1. Клиент оставляет заявку на лендинге — она только уведомляет, ничего не создаёт.
2. В `/cabinet` нажмите «Подключить клуб»: сервер создаёт `Account` владельца, `Club` и `EnrollmentKey`. Пароль показывается один раз и уходит письмом, если настроен SMTP.
3. Скачайте установщик кнопкой на карточке клуба: это zip из `SpikInstaller.exe` и готового `server.config` с `SERVER_URL` и `CLUB_KEY`.
4. На ПК клуба запустите установщик — вводить IP и порты не нужно.

Чтобы кнопка установщика работала, положите `SpikInstaller.exe` рядом с собранным сервером
(или в подпапку `Installer/`) — сервер вкладывает этот файл в архив.

## Как определяется клуб

| Кто | Чем сообщает клуб |
|---|---|
| Шелл на ПК | `X-Club-Key` из `server.config`, после логина — claim в токене |
| Админ-панель | `X-Club-Id`, взятый из `?club={id}` при переходе из кабинета |
| Кабинет | `X-Club-Id` по клику на клуб |

Права проверяет `ClubScopeMiddleware`: `PlatformAdmin` — любой клуб, `Owner` — только свои,
клубный токен — только свой. Дальше `ClubDbContext` подключается к базе `aether_club_{id}`
этого клуба, поэтому запрос физически не может увидеть данные чужого клуба.

ПК опознаётся стабильным `HardwareId` (GUID рядом с конфигом), а не MAC-адресом:
MAC меняется вместе с сетевой картой и совпадает у машин из разных клубов.

## Сеть клубов: один клиент на все филиалы

Сеть — это владелец. Все клубы одного `Account` считаются филиалами одной сети, и
посетитель у них общий: он регистрируется в одном зале, а играет в любом.

| Что | Где живёт | Область |
|---|---|---|
| Посетитель: логин, пароль, баланс, минуты, накопленные траты | Платформенная база, таблица `Clients` | Общее на сеть |
| Персонал зала | База клуба, таблица `Users` | Только свой клуб |
| Сессии, заказы, логи | База клуба | Только свой клуб |
| Пороги скидки | Запись `Club` | Свои у каждого филиала |

Из этого следуют два практических момента. Скидка считается из трат по всей сети, но
по порогам того клуба, где идёт покупка. А в карточке клиента видна история только
того зала, из которого открыли панель, — баланс при этом общий.

Логин посетителя уникален внутри сети, а не глобально: в разных сетях спокойно живут
одноимённые аккаунты. Если владельцу нужны раздельные клиенты между залами, клубы
подключаются под разными аккаунтами — это единственный способ разделить балансы.

При входе в зале сотрудник проверяется первым, поэтому его логин нельзя занять
клиентом и наоборот — обе стороны это проверяют.

## Переменные окружения

| Переменная | Обязательна | Описание |
|---|---|---|
| `SPIK_DB_CONNECTION` | Да | Строка подключения к PostgreSQL |
| `SPIK_JWT_SECRET` | Да | Ключ подписи JWT (минимум 32 символа) |
| `AETHER_ADMIN_EMAIL` | При первом запуске | Email платформенного администратора |
| `AETHER_ADMIN_PASSWORD` | При первом запуске | Его пароль |
| `SPIK_URLS` | Нет | Адреса прослушивания, по умолчанию `http://0.0.0.0:5232` |
| `PUBLIC_URL` | Нет | Публичный адрес: попадает в `server.config` установщика |
| `SPIK_CORS_ORIGINS` | Нет | Дополнительные origin, нужны только для `npm run dev` панели |
| `SPIK_SMTP_HOST` `SPIK_SMTP_PORT` `SPIK_SMTP_USER` `SPIK_SMTP_PASSWORD` | Нет | SMTP для писем с доступами |
| `TG_BOT_TOKEN` `TG_CHAT_ID` | Нет | Уведомления о заявках в Telegram |

Секретов в `appsettings.json` нет намеренно: этот файл лежит в репозитории.
Локально их можно держать в `server-settings.json` — он в `.gitignore`.

## За реверс-прокси

Сервер по умолчанию доверяет `X-Forwarded-For` и `X-Forwarded-Proto`, поэтому TLS
терминируется на nginx или Caddy. Проксировать нужно и `/clubhub` с поддержкой WebSocket.
Выключается через `BehindReverseProxy: false` в `server-settings.json`.

## CI/CD

`.github/workflows/ci.yml` собирает сервер (.NET 10), панель (Node 20), проверяет синтаксис бота
и собирает docker-образы. `release.yml` по тегу `v*` публикует образы в GHCR и создаёт релиз.

## Безопасность

- Все административные эндпоинты закрыты `[Authorize]` с ролями зала; посетитель завершает свою сессию через `/api/Auth/logout`, а не через админский `stop`.
- Клубные эндпоинты помечены `[RequireClub]`: без контекста клуба запрос отклоняется, а не выполняется по всей базе.
- Rate limiting: 5 запросов в минуту на логин, 100 на остальное API.
- Токен и ключ клуба шелл передаёт заголовками, а не в query-строке.
- Заявка с лендинга ничего не создаёт: клубы заводятся только из кабинета платформы.
